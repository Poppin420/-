# Φωνητικός Βοηθός Επιχείρησης

Mobile-first εφαρμογή (PWA) για Έλληνες ελεύθερους επαγγελματίες και μικρές επιχειρήσεις: μιλάς ελληνικά, η
εφαρμογή καταλαβαίνει μία ή περισσότερες εντολές, δείχνει κάρτα επιβεβαίωσης για την καθεμία και δεν εκτελεί
τίποτα χωρίς ρητή επιβεβαίωση.

> ⚠️ **Οι φορολογικοί κανόνες πρέπει να επαληθευτούν από λογιστή πριν από πραγματική χρήση.** Δείτε την ενότητα
> [Φορολογικές παραδοχές](#φορολογικές-παραδοχές-για-έλεγχο-από-λογιστή).

## Κατάσταση φάσεων

| Φάση | Περιεχόμενο | Κατάσταση |
|---|---|---|
| (α) | Φωνή → μεταγραφή → ανάλυση → κάρτες επιβεβαίωσης | Υλοποιημένη. **Δεν έχει δοκιμαστεί ακόμη με πραγματικό Groq.** |
| (β) | Λογαριασμοί, πελάτες, ημερολόγιο, διπλοκρατήσεις, Google Calendar, GDPR | Υλοποιημένη. **Δεν έχει δοκιμαστεί ακόμη σε Netlify/Neon ούτε με πραγματικό Google.** |
| (γ) | Προφίλ επιχείρησης, υπολογισμοί, έλεγχοι, myDATA sandbox, πάροχος για B2B | **Μερικώς.** Έτοιμα: υπολογισμοί, προφίλ, προσχέδια, αρίθμηση, 13 υποχρεωτικοί έλεγχοι, κρυπτογραφημένα κλειδιά ΑΑΔΕ, **κατάλογος κωδικών v2.0.2, XSD, παραγωγή XML, έλεγχος XSD και client της ΑΑΔΕ (SendInvoices/CancelInvoice) με unit tests**. **Επαληθεύτηκε στο πραγματικό sandbook της ΑΑΔΕ (2026-10-28):** ΑΠΥ έγινε δεκτή (Success, MARK) και ακυρώθηκε (SendInvoices + CancelInvoice). **Λείπουν:** απευθείας επιβεβαίωση προδιαγραφής/XSD από το aade.gr, πάροχος για B2B, καταγραφή τρόπου πληρωμής στο UI. **Η έκδοση παραμένει κλειδωμένη** όσο το `verified` στο `src/aade/spec.ts` είναι `false`. |
| (δ) | Πραγματικό περιβάλλον ΑΑΔΕ | Δεν έχει ξεκινήσει |

Τι έχει επαληθευτεί:

- 294 tests:
  - parsers αριθμών, ποσών, ωρών και ημερομηνιών, και 35 σενάρια ελληνικών εντολών,
  - integration tests του API πάνω σε πραγματική PostgreSQL (PGlite, μέσα στη διεργασία): σύνδεση, διπλοκράτηση,
    ταυτόχρονες κρατήσεις, επανάληψη επιβεβαίωσης, απομόνωση χρηστών, Google με προσομοιωμένα endpoints, εξαγωγή
    και διαγραφή δεδομένων,
  - κρυπτογράφηση (AES-256-GCM), κωδικοί (scrypt), αναγνώριση ονομάτων σε όλες τις πτώσεις,
  - υπολογισμοί παραστατικών: unit tests και property-based tests (fast-check), με στρογγυλοποιήσεις, πολλούς
    συντελεστές ΦΠΑ, εκπτώσεις, απαλλαγές και παρακρατήσεις,
  - ένα test για κάθε υποχρεωτικό έλεγχο έκδοσης, που αποδεικνύει ότι μπλοκάρει όταν παραβιάζεται,
  - προστασία εκδοθέντων παραστατικών στη βάση: ούτε αλλαγή ούτε διαγραφή, μόνο ακύρωση,
  - παραγωγή XML myDATA που επικυρώνεται έναντι των επίσημων XSD v2.0.2, ανάλυση απόκρισης της ΑΑΔΕ, ο client
    (SendInvoices/CancelInvoice) με προσομοιωμένες αποκρίσεις, και η πλήρης ροή έκδοσης πάνω σε πραγματική βάση
    (επιτυχία, ρητή απόρριψη, άγνωστη έκβαση και η επαναχρησιμοποίηση αριθμού κατά Φ4).
- Πλήρης ροή σε browser (Chromium, οθόνη κινητού) με τα πραγματικά endpoints και PGlite, ψεύτικα μόνο το LLM και η
  Google: εγγραφή → φωνητική εντολή → κλείσιμο ραντεβού → μπλοκάρισμα διπλοκράτησης → ερώτηση προγράμματος →
  προβολή εβδομάδας → ακύρωση → εξαγωγή → διαγραφή λογαριασμού.

Τι **δεν** έχει επαληθευτεί:

- Πραγματικές κλήσεις σε Groq Whisper και Groq LLM. Τρέξτε `GROQ_API_KEY=... npm run eval:llm` και δείτε
  [Αξιολόγηση LLM](#αξιολόγηση-llm).
- Πραγματική σύνδεση OAuth με Google και εγγραφή γεγονότων.
- **Παραγωγική ΑΑΔΕ (φάση δ).** Στο **δοκιμαστικό** περιβάλλον έχει γίνει επιτυχημένος κύκλος (έκδοση ΑΠΥ +
  ακύρωση, 2026-10-28). Στο **πραγματικό** δεν έχει γίνει τίποτα. Επίσης τα XSD/κωδικοί δεν έχουν επιβεβαιωθεί
  απευθείας από το aade.gr (δες Φ5 και `src/aade/xsd/v2.0.2/PROVENANCE.md`), και ο αυτοματοποιημένος έλεγχος
  sandbox δεν τρέχει στη σουίτα (χρειάζεται δοκιμαστικά κλειδιά ως secrets). Γι' αυτό το `verified` είναι `false`
  και η έκδοση μένει κλειδωμένη.
- **Κανόνες που αποκάλυψε το sandbox** (ενσωματωμένοι στον builder): ο τρόπος πληρωμής (`paymentMethods`) είναι
  **υποχρεωτικός** για παραστατικά λιανικής (σφάλμα 204), το `itemDescr` ανά γραμμή **απαγορεύεται** στη λιανική
  (σφάλμα 247), και ο ΑΦΜ του εκδότη πρέπει να ταυτίζεται με αυτόν του λογαριασμού των κλειδιών (σφάλμα 105).
- Λειτουργία σε Netlify Functions με Neon PostgreSQL. Ο κώδικας χρησιμοποιεί τον standard driver `pg`, και το
  migration θέλει την επέκταση `btree_gist`, που το Neon υποστηρίζει.
- Ηχογράφηση σε πραγματικές συσκευές iOS/Android.
- Τα όρια χρόνου, μεγέθους και rate limiting των Netlify Functions στο δικό σας πλάνο.

### Ημερολόγιο και διπλοκράτηση

- Κάθε κάρτα ξαναχτίζεται και ξαναελέγχεται στον server πριν από την προεπισκόπηση και πριν από την εκτέλεση.
  Ό,τι υπολόγισε ο browser δεν θεωρείται αξιόπιστο.
- Η διπλοκράτηση ελέγχεται σε τρία σημεία:
  - στην προεπισκόπηση, όπου η επικάλυψη με άλλο ραντεβού μπλοκάρει την επιβεβαίωση,
  - πριν την εγγραφή στη βάση,
  - στην ίδια τη βάση, με περιορισμό που απαγορεύει επικαλυπτόμενα ενεργά ραντεβού και ισχύει ακόμη και για
    ταυτόχρονα αιτήματα.
- Τα γεγονότα του Google Calendar εμφανίζονται ως **προειδοποίηση**, όχι ως μπλοκάρισμα, γιατί μπορεί να είναι
  προσωπικά.
- Κάθε επιβεβαιωμένη κάρτα εκτελείται μία φορά: αν το κουμπί πατηθεί δύο φορές, επιστρέφεται το ίδιο αποτέλεσμα.
- Ο πελάτης αναγνωρίζεται σε όλες τις πτώσεις («Μαρίας» → «Μαρία Παπαδοπούλου»). Αν ταιριάζουν πολλοί, η κάρτα
  ρωτάει. Αν δεν ταιριάζει κανείς, δημιουργείται νέος πελάτης, κάτι που φαίνεται στην κάρτα.
- Η μετακίνηση ραντεβού κρατά την αρχική διάρκεια.
- Ο συγχρονισμός με Google είναι μονόδρομος (εφαρμογή → Google). Αν αποτύχει, το ραντεβού μένει κανονικά και στο
  ημερολόγιο εμφανίζεται κουμπί επανάληψης.

### Βασικός κανόνας: το LLM δεν υπολογίζει τίποτα

1. Το LLM χωρίζει την εντολή σε ενέργειες και **αντιγράφει αυτούσια** κομμάτια του κειμένου (π.χ.
   `time_text: "πέντε το απόγευμα"`). Δεν μετατρέπει, δεν υπολογίζει, δεν συμπληρώνει.
2. Κάθε κομμάτι πρέπει να υπάρχει στη μεταγραφή. Αν το LLM «εφεύρει» όνομα ή ποσό, η κάρτα ρωτάει.
3. Ημερομηνίες, ώρες, ποσά και ποσότητες τα ερμηνεύει ντετερμινιστικός κώδικας.
4. Ό,τι λείπει ή είναι διφορούμενο γίνεται ερώτηση: «στις 5» (πρωί ή απόγευμα;), «την επόμενη Παρασκευή»,
   «περίπου 100 ευρώ», ποσό με ή χωρίς ΦΠΑ, τιμή ανά μονάδα ή συνολική.
5. Στο LLM στέλνεται μόνο η μεταγραφή. Δεν στέλνονται ημερομηνία, πελατολόγιο, ΑΦΜ ή κλειδιά.

### Γιατί αυτές οι τεχνικές επιλογές

- **PWA αντί για native app:** δεν χρειάζεται app store, ενημερώνεται αμέσως και η ηχογράφηση δουλεύει σε
  Android και iOS Safari 14.3+.
- **TypeScript σε Netlify Functions:** η φιλοξενία είναι στο Netlify, που δεν τρέχει Python στις Functions.
  Frontend και backend μοιράζονται τους ίδιους parsers, οπότε οι απαντήσεις στις κάρτες ερμηνεύονται με τον ίδιο
  κώδικα.
- **Groq** για μεταγραφή και LLM. Ο πάροχος LLM αλλάζει υλοποιώντας το `IntentLLM`.

### Τιμολόγηση (φάση γ)

Η ροή από τη φωνή μέχρι την έκδοση:

1. **Η κάρτα «Προσχέδιο παραστατικού».** Από το προφίλ επιχείρησης επιλέγονται:
   - ο τύπος παραστατικού, ανάλογα με τον πελάτη: με ΑΦΜ → επιχείρηση, χωρίς → ιδιώτης,
   - η κατηγορία ΦΠΑ κάθε γραμμής: από τον κατάλογο υπηρεσιών αν υπάρχει αντιστοίχιση, αλλιώς η προεπιλογή του
     προφίλ, πάντα ορατή και με δυνατότητα αλλαγής,
   - οι κρατήσεις.

   Ο κώδικας υπολογίζει όλα τα ποσά με δεκαδικούς σταθερής ακρίβειας.
2. **Αποθήκευση προσχεδίου.** Από τη φωνή φτάνει μόνο μέχρι εδώ.
3. **Καρτέλα «Παραστατικά».** Δείχνει όλα τα φορολογικά στοιχεία όπως θα σταλούν, τη λίστα των υποχρεωτικών
   ελέγχων και το κουμπί **«Έκδοση»**, που ενεργοποιείται μόνο όταν περνούν όλοι οι έλεγχοι. Ο server απαιτεί
   ρητή επιβεβαίωση και ξανατρέχει τους ελέγχους.

Υποχρεωτικοί έλεγχοι (`src/invoicing/invoices.ts`). Αν αποτύχει έστω ένας, η έκδοση μπλοκάρει:

| Κωδικός | Τι ελέγχει |
|---|---|
| `spec_verified` | Ο κατάλογος κωδικών και τα XSD έχουν επαληθευτεί. **Αποτυγχάνει όσο `verified = false`** (ο κατάλογος έχει φορτωθεί αλλά δεν έχει επιβεβαιωθεί απευθείας από το aade.gr). |
| `profile_complete` | Το προφίλ είναι πλήρες και ελεγμένο από λογιστή. |
| `issuer_afm` / `customer_afm` | Έγκυροι ΑΦΜ εκδότη και πελάτη (ο πελάτης υποχρεωτικά όταν είναι επιχείρηση). |
| `document_type_compatible` | Ο τύπος υπάρχει στο προφίλ και ταιριάζει στον πελάτη. |
| `required_fields` | Υπάρχουν τα γνωστά υποχρεωτικά πεδία. TODO: τα πλήρη υποχρεωτικά πεδία ανά τύπο, από την προδιαγραφή. |
| `totals_consistent` | Καθαρή αξία + ΦΠΑ = σύνολο, ανά γραμμή και συνολικά, και ο νέος υπολογισμός συμφωνεί με τον αποθηκευμένο. |
| `issue_date` | Η ημερομηνία έκδοσης είναι η σημερινή. TODO: το επιτρεπτό διάστημα, από την προδιαγραφή. |
| `numbering` | Υπάρχει σειρά και δεν εκκρεμεί άλλο παραστατικό της ίδιας σειράς. Τη μοναδικότητα του αριθμού την εγγυάται και η βάση. |
| `not_already_sent` | Το παραστατικό είναι ακόμη προσχέδιο, με μοναδικό κλειδί αποστολής. |
| `environment` | Επιτρέπεται μόνο το δοκιμαστικό περιβάλλον μέχρι τη φάση (δ). |
| `credentials` | Υπάρχουν κλειδιά myDATA για το περιβάλλον. |
| `channel` | Τα B2B περνούν από πιστοποιημένο πάροχο (Φ1). Σήμερα δεν έχει οριστεί πάροχος. |

Η βάση προστατεύει τα παραστατικά που στάλθηκαν:
- **Εκδοθέν:** δεν αλλάζει. Επιτρέπεται μόνο η ακύρωση.
- **Οτιδήποτε έφτασε στην ΑΑΔΕ:** δεν διαγράφεται, και η διαγραφή λογαριασμού μπλοκάρει όσο υπάρχουν τέτοια
  παραστατικά.
- **XML που στάλθηκε:** δεν αλλάζει ποτέ.

## Εγκατάσταση

Απαιτείται Node.js 20+.

```bash
npm install
npm test           # unit + integration tests (in-process PostgreSQL, no external services)
npm run typecheck
npm run build
# Live myDATA sandbox round-trip (opt-in, needs test keys as a Network secret + MYDATA_TEST_AFM):
MYDATA_TEST_AFM=... npm run test:sandbox
```

### Ανάπτυξη στο Netlify

1. Συνδέστε το repo στο Netlify. Η εντολή build και ο φάκελος δημοσίευσης ορίζονται στο `netlify.toml`.
2. Προσθέστε βάση PostgreSQL. Η πιο απλή επιλογή είναι το **Netlify DB** (Neon), που ορίζει μόνο του το
   `NETLIFY_DATABASE_URL`. Αλλιώς ορίστε το `DATABASE_URL` για οποιαδήποτε PostgreSQL 14+ με την επέκταση
   `btree_gist`. Προτιμήστε περιοχή στην ΕΕ.
3. Τρέξτε τα migrations μία φορά, και ξανά σε κάθε νέα έκδοση:
   `DATABASE_URL=... npm run db:migrate`
4. Ορίστε τις μεταβλητές περιβάλλοντος του παρακάτω πίνακα.

Τοπικά: `cp .env.example .env`, συμπληρώστε και τρέξτε `netlify dev`.

## Ρύθμιση κλειδιών

Όλες οι μεταβλητές μένουν **μόνο στον server**. Στο Netlify μπαίνουν στο *Site configuration → Environment
variables* και δηλώνονται ως secret.

| Μεταβλητή | Υποχρεωτική | Σημειώσεις |
|---|---|---|
| `DATABASE_URL` / `NETLIFY_DATABASE_URL` | Ναι | Χωρίς βάση, το API απαντά 503. |
| `APP_BASE_URL` | Ναι | Η δημόσια διεύθυνση της εφαρμογής. Χρησιμοποιείται για τον έλεγχο προέλευσης των αιτημάτων και για το redirect της Google. Στο Netlify, αν λείπει, χρησιμοποιείται το `URL`. |
| `SIGNUP_CODE` | Για εγγραφές | Κωδικός πρόσκλησης, τουλάχιστον 8 χαρακτήρες. Αν είναι κενό, οι εγγραφές είναι κλειστές. |
| `GROQ_API_KEY` | Για φωνή | Από https://console.groq.com. Δεν φτάνει ποτέ στον browser και δεν καταγράφεται σε logs. |
| `GROQ_LLM_MODEL` | Όχι | Προεπιλογή: `llama-3.3-70b-versatile`. Ελέγξτε ότι το μοντέλο είναι διαθέσιμο στο Groq. |
| `DATA_ENCRYPTION_KEY` | Για Google | 32 τυχαία bytes σε base64 (`openssl rand -base64 32`). Κρυπτογραφεί τα διακριτικά κάθε χρήστη. **Αν χαθεί, οι συνδέσεις Google πρέπει να γίνουν ξανά.** Στη φάση (γ) θα κρυπτογραφεί και τα κλειδιά myDATA. |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Όχι | OAuth client τύπου «Web application» στο Google Cloud Console, με Authorized redirect URI `https://<site>/api/google/callback` και ενεργοποιημένο το Google Calendar API. Scope: `calendar.events`. |

Τα διαπιστευτήρια myDATA (όνομα χρήστη και subscription key) **δεν** είναι μεταβλητές περιβάλλοντος: κάθε
χρήστης θα τα εισάγει ο ίδιος στη φάση (γ) και θα αποθηκεύονται κρυπτογραφημένα (AES-256-GCM) ανά χρήστη.

## Αξιολόγηση LLM

```bash
GROQ_API_KEY=... npm run eval:llm
```

Στέλνει τις 35 εντολές του `tests/fixtures/commands.ts` στο πραγματικό μοντέλο και ελέγχει ότι οι κάρτες
βγαίνουν ίδιες με τα unit tests. Επειδή η έξοδος ενός LLM μπορεί να αλλάξει από έκδοση σε έκδοση, πρόκειται για
αξιολόγηση και όχι για unit test.

## Ασφάλεια και απόρρητο

- **Λογαριασμοί:**
  - εγγραφή μόνο με κωδικό πρόσκλησης,
  - κωδικοί με scrypt (N=2^17),
  - session cookie `__Host-` με HttpOnly, Secure και SameSite=Lax, ενώ στη βάση αποθηκεύεται μόνο το SHA-256 του
    session,
  - κλείδωμα για 15′ μετά από 10 αποτυχημένες προσπάθειες σύνδεσης,
  - το μήνυμα λάθους δεν αποκαλύπτει αν υπάρχει το email.
- **Αιτήματα που αλλάζουν δεδομένα:** απορρίπτονται αν έρχονται από άλλη προέλευση (Origin).
- **Απομόνωση χρηστών:** κάθε ερώτημα στη βάση φιλτράρεται με τον χρήστη. Τα tests ελέγχουν ότι ένας χρήστης δεν
  βλέπει, δεν ακυρώνει και δεν ξαναεκτελεί κάρτες άλλου.
- **Διακριτικά Google:** κρυπτογραφούνται με AES-256-GCM, δεμένα στον χρήστη και στον σκοπό τους. Το OAuth γίνεται
  με PKCE και state μιας χρήσης που λήγει σε 10′.
- **Ήχος:** μένει μόνο στη μνήμη κατά τη μεταγραφή και δεν γράφεται πουθενά. Το κείμενο της εντολής δεν
  αποθηκεύεται, εκτός από τα στοιχεία των ενεργειών που επιβεβαιώνει ο χρήστης.
- **Logs:** καταγράφουν μόνο το στάδιο, τον τύπο σφάλματος και τον κωδικό HTTP. Ποτέ κείμενο, ήχο, διακριτικά ή
  κλειδιά.
- **GDPR:**
  - εξαγωγή όλων των δεδομένων σε JSON,
  - οριστική διαγραφή λογαριασμού με επιβεβαίωση κωδικού, που ανακαλεί και τη σύνδεση Google,

## Ανοιχτά θέματα

### Τι μπλοκάρει την ολοκλήρωση της φάσης (γ)

Η παραγωγή XML, ο έλεγχος XSD, ο client και τα unit tests είναι έτοιμα. Για να **ξεκλειδώσει** η έκδοση
(`verified = true`) μένουν:

1. **Απευθείας επιβεβαίωση από το `aade.gr`.** Τα XSD και οι κωδικοί πάρθηκαν από mirror γιατί το aade.gr ήταν
   απρόσιτο (Akamai 403). Πρέπει να συγκριθούν με τα αρχεία που κατεβαίνουν απευθείας από το aade.gr και να τα
   εγκρίνει λογιστής. Δες `src/aade/xsd/v2.0.2/PROVENANCE.md`.
2. **Καταγραφή τρόπου πληρωμής στο UI.** Το sandbox απαιτεί `paymentMethods` για τη λιανική· ο builder το
   υποστηρίζει και το endpoint το απαιτεί, αλλά η κάρτα/ροή πρέπει να το ζητά από τον χρήστη (μετρητά, POS, κ.λπ.).
3. **Integration test στο sandbox** — υπάρχει και περνά (`npm run test:sandbox`): αυθεντικοποίηση, έκδοση ΑΠΥ
   που γίνεται δεκτή, και ακύρωση. Χρειάζεται τα δοκιμαστικά κλειδιά ως Network secret (headers `aade-user-id`,
   `ocp-apim-subscription-key` στο `mydataapidev.aade.gr`) και `MYDATA_TEST_AFM`. Παρακάμπτεται στο κανονικό `npm test`.
4. **Πιστοποιημένος πάροχος ηλεκτρονικής τιμολόγησης** για τα B2B: ποιος πάροχος, με ποιο API, με ποιον τρόπο
   σύνδεσης ανά χρήστη. Μέχρι τότε εκδίδονται απευθείας μόνο παραστατικά προς ιδιώτες (Φ1, Φ2).
5. **Έλεγχος παρακράτησης στο sandbox** (Φ14): η κατανομή ανά γραμμή και τα σύνολα πρέπει να γίνουν δεκτά σε
   πραγματικό B2B παραστατικό (ο βασικός κύκλος λιανικής χωρίς παρακράτηση έχει ήδη γίνει δεκτός).

### Λοιπά

- Απευθείας λήψη της προδιαγραφής και των XSD από το `aade.gr` για επιβεβαίωση του mirror (φάση γ· δες πιο πάνω).
- Επιλογή πιστοποιημένου παρόχου ηλεκτρονικής τιμολόγησης με δημόσιο API για τα B2B (φάση γ).
- Όταν η εντολή λέει «30 ευρώ την ώρα», η κάρτα ρωτάει ακόμη αν το ποσό είναι ανά μονάδα ή συνολικό.
- Τα επικαλυπτόμενα ραντεβού απαγορεύονται πάντα. Για επαγγέλματα με ομαδικά ή παράλληλα ραντεβού (γυμναστήρια,
  ιατρεία με πολλές αίθουσες) θα χρειαστεί ρύθμιση στο προφίλ.
- Η προεπιλεγμένη διάρκεια ραντεβού είναι 60′ (φαίνεται ως παραδοχή στην κάρτα). Θα γίνει ρύθμιση του προφίλ ή
  της υπηρεσίας στη φάση (γ).
- Ένας νέος πελάτης αποθηκεύεται με το όνομα όπως ειπώθηκε, που μπορεί να είναι σε γενική πτώση (π.χ. «Μαρίας»).
  Διορθώνεται από την κάρτα πριν την επιβεβαίωση.
